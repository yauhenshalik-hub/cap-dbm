# Schema Migration

CAP defines the schema; the versioned migrations in `db/migrations/` apply it. They are the only
schema writer in all environments — `cds deploy` against a live database is never used for
production schema evolution.

Every change ships as a numbered **state**, generated by this tool. The mechanics of a state (folder
layout, artifacts, error messages) are documented in
[State-Based Database Migrations](state-based-migrations.md). This guide covers _when_ to create a
state and how to sequence a breaking change safely.

---

## Making a schema change

### Minor change (backwards-compatible)

Add column, add index, new table — deploy in a single PR without downtime.

1. Edit `db/schema.cds` (or the relevant `.cds` file).

2. Generate the next state:

   ```sh
   npx cap-dbm delta
   ```

   This produces, with `<N>` derived from the highest `V<n>` in `db/migrations/`:

   ```text
   db/migrations/V<N>__migration.sql   one file, one transaction: DDL delta + DML placeholder
   ```

   It also refreshes `db/snapshots/schema.csn`, the snapshot the _next_ delta is computed against.

   The command warns if any lossy statement is detected — follow
   [Major change](#major-change-breaking) instead.

3. Review the generated DDL and append DML at the bottom of the file if the change needs code-list
   rows or a backfill.

4. Commit the `.cds` change, `V<N>__migration.sql` and `db/snapshots/schema.csn` in one PR. Run
   `npx cap-dbm check` (or wire it into your pipeline) to fail the PR if the snapshot and
   the migrations disagree.

The migration should be applied before the CAP deployment on every merge to your main branch.

---

### Major change (breaking)

Drop column, rename, type change — requires four separate releases to keep the running app
compatible at every step. Each release is its own state.

#### Release 1 — Expand

Add the replacement structure alongside the old one. The old structure stays untouched.

```sh
# Edit db/schema.cds to add the new column/table
npx cap-dbm delta
```

Deploy. Both old and new structure exist in the DB.

#### Release 2 — Migrate

Deploy app code that writes to both old and new structure. Backfill existing data into the new
structure by writing the `INSERT` / `UPDATE` statements at the bottom of `V<N>__migration.sql` for this state.

```sh
npx cap-dbm delta
```

#### Release 3 — Switch

Deploy app code that reads and writes only from the new structure. Verify no consumer uses the old
structure. No DDL change in this release — `cap-dbm delta` will report `No schema changes
detected`, which is expected; no state is created.

#### Release 4 — Contract

Remove the old structure. This is where the `DROP` lives, and the only release where a lossy warning
from `cap-dbm delta` is acceptable.

```sh
# Edit db/schema.cds to remove the old column/table
npx cap-dbm delta
```

> Applied migrations are never rolled back. If a deployment fails after a state runs, the previous
> app version continues against the migrated schema. Corrections go forward as a new state — never
> edit or delete an applied migration or its Flyway history record.

## Re-baselining the snapshot only

`db/snapshots/schema.csn` is what `cap-dbm delta` diffs against. Both state commands
refresh it automatically, so you normally never run this by hand. Use it only to re-baseline (e.g.
after resolving a merge conflict on the snapshot):

```sh
npm run capture
```

> `npm run capture` snapshots whatever your `.cds` files look like right now. If they already contain
> unreleased changes, those changes end up in the baseline and the next delta silently omits them.
> To regenerate a bad state instead: delete `V<N>__migration.sql`, run
> `git checkout db/snapshots/schema.csn`, then re-run `npx cap-dbm delta`.

---

## Naming and numbering

```text
db/migrations/V<N>__migration.sql
```

- `<N>` is auto-incremented by the state commands, which scan `db/migrations/V<n>*`.
- One file per state: DDL and DML live in the same migration and the same transaction.
- Never rename or delete an applied migration.

## Resetting a development database

Editing a migration that Flyway has already applied changes its checksum, and the next run aborts:

```text
ERROR: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 2
```

On a **throwaway dev database only**, the sanctioned fix is to drop it and let the pipeline rebuild it
from `V1` using your own infrastructure tooling (e.g. deleting and recreating the database resource).
A dev database that holds no data worth keeping can safely be recreated empty and repopulated by the
migrations themselves.

> **Never on test or prod** — those hold real data, and applied migrations and Flyway history records
> must not be edited or deleted there. A bad migration is corrected by shipping the next state
> forward, or with `flyway repair` if only the history record is wrong. This dev-only exception
> expires the moment a version has been applied to a shared environment.

## First state only

A brand-new database gets its baseline from:

```sh
npx cap-dbm init
```

This emits the full schema instead of a delta. Use it only when no state exists yet — every state
after that comes from `npx cap-dbm delta`.

---

## Hand-written SQL

Objects that are not part of the CDS model are never generated and must be written by hand into the
migration. Applied migrations are frozen by checksum, so never add to an existing one: put further
hand-written objects in a **new** migration.

Prefer a CDS-native construct where one exists — e.g. a `stored` calculated column plus
`@assert.unique` instead of a hand-written partial index — so the constraint is part of the model and
every future delta carries it automatically.

---

## How it applies

Flyway (or an equivalent migration runner) applies the migrations in your deployment pipeline,
running every unapplied `V*.sql` in order.

To apply a state by hand locally:

```sh
psql -v ON_ERROR_STOP=1 -f db/migrations/V<N>__migration.sql
```

Everything runs in a single transaction — DDL and DML apply completely or not at all.

All unapplied `V*.sql` files should be applied before the CAP app starts. The CAP runtime should
connect with a role that has DML only — no DDL privilege — so schema changes can only land through
this migration flow.
